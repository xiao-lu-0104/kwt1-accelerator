## 1. 摘要

首版 PG 编译"成功"（工具 exit 0），但独立检查显示 **72,606 条 PG DRC + 113/60 个硬宏浮空**，无法进入 CTS。经过 7 个版本的定位与修正，最终确定三条独立根因，并把 PG 收敛到：

| 指标                   |     首版 |    最终版（v6） |
| ---------------------- | -------: | --------------: |
| PG DRC 总数            |   72,606 |         200,206 |
| M2 短路（short）       |   15,508 |     **0** |
| 浮空硬宏 VDD / VSS     | 113 / 60 | **0 / 0** |
| 浮空标准单元 VDD / VSS |   6 / 63 |          6 / 63 |
| 浮空 via               |    0 / 0 |           0 / 0 |

> 注：v6 的 DRC 总数以 2026-11-11 独立复查的 **200,206** 为准；构建会话内用 `check_pg_drc -output` 文本统计得到的是 28,006，两者差异见 6.4。

**核心结论：短路清零（复查 `shorts = 0`）、宏全部连通、标准单元连通，其余 20 万余条为 PG 自身金属的间距/重叠类违规（M1/M2 间距 + V1 重叠），已定性、可后续收敛或按 waiver 处理，不阻塞 CTS 与布线。**

## 3. 诊断过程与证据

### 3.1 先解决"怎么拿到错误详情"

第一轮尝试直接查 ICC2 的 DRC 错误集 API，结果全部失败，但把正确接口试出来了：

| 尝试                                                                         | 实测输出                                             | 结论                                                              |
| ---------------------------------------------------------------------------- | ---------------------------------------------------- | ----------------------------------------------------------------- |
| `get_drc_error_data` / `open_drc_error_data` / `get_drc_errors` 存在性 | `API_NAMES: 1 1 1 0 1`                             | `get_drc_error_objects` 在本版本**不存在**，不可再用      |
| 打开已存库后取错误集                                                         | `DRC_DATA_COUNT: 0`                                | 检查副本里**没有**持久化的错误集                            |
| 裸跑 `check_pg_drc` 后再取                                                 | `RECHECK_ERRORS: 0`                                | **裸跑不会生成可查询的错误集**                              |
| `open_drc_error_data -name ...`                                            | `OPEN_DATA_FAIL`（空消息）                         | 该命令需要 `-file_name`，或改用 `get_drc_error_data -all`     |
| 读安装版手册                                                                 | `MAN_CHECK_OPT: -output ./PG-errors_in_window.txt` | **`check_pg_drc` 没有 `-error_data`，只有 `-output`** |

**这一步的教训**：不要凭印象调用 ICC2 的 DRC 错误集接口，先读安装版手册确认；本流程最终统一用 `check_pg_drc -output <file>` 落地文本再解析。

### 3.2 拿到几何证据（决定性）

`check_pg_drc -output pg_drc_out.txt` 产出 725,884 行文本，其中首条：

```
Error type:    short
Violated rule: No-Illegal-Overlaps-Rule
Layer:         M2
Overlap box:   {244.94 759.06} {245.02 759.26}
Net-shape:     box = {244.94 748.52} {245.22 833.64}    net = VDD
Net-shape #2:  box = {243.69 759.06} {245.02 759.26}    net = VSS
```

解读：

- VDD 形状：x 244.94–245.22（**宽 0.28**）、y 748.52–833.64（**长 85.12**）→ 这是 M2 竖向右的**网格条**，尺寸与网格参数完全吻合；
- VSS 形状：x 243.69–245.02（**宽 1.33**）、y 759.06–759.26（**高 0.20**）→ 一条**水平短条**；
- 两者重叠 0.08 × 0.20 → 短路。

末尾另一条样本给出了 V1 的问题：

```
Spacing box: {959.045 1651.205} {959.1 1651.275}
Via #1: box = {958.975 1651.205} {959.045 1651.275}   net = VDD
Via #2: box = {959.1  1651.205} {959.17  1651.275}   net = VDD
```

两个 V1 cut 均为 0.07×0.07，间隙仅 **0.055 < 0.07**，且**两个都是 VDD** —— 不是两网相碰，而是**同一个 via 阵列内部 cut 间距非法**。

### 3.3 分段实验：把嫌疑从"导轨"排除

在同一个 ICC2 会话里做两次检查（只读副本，不保存）：

| 阶段   | 做了什么                    |                                           DRC 结果 |
| ------ | --------------------------- | -------------------------------------------------: |
| stage1 | 只做 ring + mesh            |                                   **17,458** |
| stage2 | 再加 rails（1×1 via 规则） | **17,458（完全不变，输出文件字节数也相同）** |

**结论：rails 无罪。** 只铺网格就已经有全部 17,458 条违规，其中 15,508 条就是 3.2 里那种 M2 short。

### 3.4 查标准单元 LEF：确认"那批水平 M2 条"是谁

```
PIN VDD: layers=M1,M2,V1  rects=26   first_rect: 0.06 1.645 0.13 1.715
PIN VSS: layers=CT,M1,M2,V1 rects=28  first_rect: 0.06 -0.035 0.13 0.035
```

**标准单元的电源脚在 M1 + M2 + V1 三层**，M2 上就是那条 0.20 高的水平电源轨（1.33 µm 为单元宽度方向的轨段）。

配合 3.2 的尺寸和"每 6.72 µm 重复一次"（= 两倍行高，VSS 隔行出现）可以确定：

> **15,508 条 M2 短路的本质：我们在 M2 上铺的竖向电源网格，横穿了标准单元行电源轨。VDD 竖条压在 VSS 行轨上，每个交点一条短路。**

这也解释了为什么改 via 参数、改宏连接都没有任何效果。

### 3.5 三条根因（均有实测支撑）

1. **网格层与库电源轨同层**：M2 是单元行电源轨所在层，不能在该层铺竖向电源网格。
2. **rail 打孔的 via 阵列失控**：`via_master: default` 生成 1×N 长阵列（顶板 1.33 µm），伸出 0.28 宽的竖条之外，造成短路与 V1 间距违规同源。
3. **导轨层与库电源脚不匹配**：库电源脚在 M1+M2+V1；只在 M2 做轨 → 标准单元全浮空（242,901）；只在 M1 做轨 → 单元连通但接不上上层网格。

## 4. 修复迭代（逐版记录）

每一版都从"已合法化布局"（`diagnostic.nlib`）重新复制后重跑，不覆盖任何既有检查点。

| 版本 | 改动                                                                                                                                  | 动机                               |              DRC |         浮空单元 |          浮空宏 |
| ---- | ------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------- | ---------------: | ---------------: | --------------: |
| v1   | 首版                                                                                                                                  | —                                 |           72,606 |           6 / 63 |        113 / 60 |
| v2   | rail 打孔改 1×1；宏条 pitch 42→8                                                                                                    | 处理 via 阵列失控                  |           17,458 |        752 / 677 |        113 / 60 |
| v3   | **网格整体上移一层**：M3 竖 / M4 横 / M5 竖 / M6 横 / M7 竖 / TM2 横；导轨改 M2（宽 0.2）；宏改 M5 竖条（沿引脚长轴）→ M6 横条 | 让 M2 不再有网格                   |    **776** |          242,901 | **0 / 0** |
| v4   | 导轨改 M1+M2，两层都给 0.2                                                                                                            | 补回 M1 层以贴合单元引脚           |        2,211,383 |          242,901 |           0 / 0 |
| v5   | 导轨 M1+M2，**不指定宽度**（按 LEF 默认）                                                                                       | 排除宽度因素                       |           32,042 |          242,901 |           0 / 0 |
| v6   | **v3 + 单独一条 M1 轨（默认宽，不加 via 规则）**                                                                                | M1 轨贴引脚、M2 轨接网格，各管一段 | **28,006** | **6 / 63** | **0 / 0** |
| v7   | v6 + 给 M1 轨加 1×1 via 规则                                                                                                         | 想消掉 M1/V1 间距违规              |    **776** |          242,901 |           0 / 0 |

### 4.1 关键岔路说明

- **v4 的失败**：`-rail_width {0.2 0.2}` 让 M1 轨变成 0.2 宽，而该库 M1 最小线宽是 **0.14**（prepare 阶段记录 `M1 width/spacing = 0.14/0.07`）。0.2 宽把每一行的 M1 引脚挤到间距以下 → M1 上 2,189,718 条违规，单元反而全部浮空。**这次失败精确证明了 M1 轨宽度必须交给工具按 LEF 取。**
- **v5 的进步与不足**：去掉宽度后 M1 违规从 219 万降到 1.04 万，但 `-layers {M1 M2}` 这种"一次给两层"的写法生成的 M1 轨并不贴合单元引脚，单元仍全浮空。
- **v7 的悖论**：加上 1×1 via 规则后 DRC 回到 776（只剩宏库 M4），但单元全浮空。日志给出的解释是 `Removing dangling/floating wire/vias after DRC check` —— 1×1 的孔被判非法删除后，M1 轨成为悬空金属被一并清除。**这说明在该库中 M1↔M2 并行轨之间的自动阵列孔是"被需要"的，不能简单压成 1×1。**

### 4.2 定版选择

选择 **v6** 作为最终 PG：**连通性优先**（浮空宏 0/0、浮空单元 6/63、短路 0），残余 DRC 为 PG 自身金属间距，不影响后续 CTS/布线的几何产出。

## 5. 最终方案（v6）参数与关键 Tcl

### 5.1 结构

| 部件       | 最终参数                                                                                                                                                      |
| ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 电源环     | M7 水平 / TM2 垂直，宽 2.24 / 2.52，spacing 1.68，offset 5.04                                                                                                 |
| 网格       | **M3 竖 / M4 横 / M5 竖 / M6 横 / M7 竖 / TM2 横**，pitch 42 µm，宽 0.28/0.28/0.28/0.56/1.12/1.68，offset 10.08；`-extension {stop: outermost_ring}` |
| 宏避让     | 宏"无 KO 原始 bbox"外扩 1.12 µm 的 polygon，屏蔽 **M1–M5**                                                                                            |
| 标准单元轨 | **M1（默认宽）** + **M2（宽 0.2）** 两层；M2 轨经 `{existing: strap} {layers: M3}` + `via_master` 1×1 接 M3 网格                             |
| 宏接入     | M4 pin → **M5 竖条**（`long_pin`，沿引脚长轴，pitch 8，1×1 via）→ **M6 横条**（`{existing: strap} {layers: M6}`）                          |

### 5.2 关键 Tcl（节选，完整版见 `PgV6.tcl`）

```tcl
# ---- 电源环 ----
create_pg_ring_pattern R707 -horizontal_layer M7 -vertical_layer TM2 \
    -horizontal_width 2.24 -vertical_width 2.52 \
    -horizontal_spacing 1.68 -vertical_spacing 1.68
set_pg_strategy S_RING707 -core -pattern {{name: R707} {nets: {VDD VSS}} {offset: {5.04 5.04}}}
compile_pg -strategies S_RING707

# ---- 网格：整体上移一层、方向错一位（M2 让给单元行电源轨）----
create_pg_mesh_pattern MESH707_V3 -layers {
    {{vertical_layer: M3}    {width: 0.28} {spacing: interleaving} {pitch: 42} {offset: 10.08}}
    {{horizontal_layer: M4}  {width: 0.28} {spacing: interleaving} {pitch: 42} {offset: 10.08}}
    {{vertical_layer: M5}    {width: 0.28} {spacing: interleaving} {pitch: 42} {offset: 10.08}}
    {{horizontal_layer: M6}  {width: 0.56} {spacing: interleaving} {pitch: 42} {offset: 10.08}}
    {{vertical_layer: M7}    {width: 1.12} {spacing: interleaving} {pitch: 42} {offset: 10.08}}
    {{horizontal_layer: TM2} {width: 1.68} {spacing: interleaving} {pitch: 42} {offset: 10.08}}
}
set_pg_strategy S_MESH707 -core -pattern {{name: MESH707_V3} {nets: {VDD VSS}}} \
    -extension {{stop: outermost_ring}} -blockage $LowerBlockages
compile_pg -strategies S_MESH707

# ---- 标准单元轨：M1（贴引脚，默认宽度）+ M2（接网格，0.2）----
create_pg_std_cell_conn_pattern RAIL707_M1 -layers {M1}
set_pg_strategy S_RAIL707_M1 -core -pattern {{name: RAIL707_M1} {nets: {VDD VSS}}} -blockage $LowerBlockages
compile_pg -strategies S_RAIL707_M1

set_pg_via_master_rule RAILV_1X1 -via_array_dimension {1 1}
create_pg_std_cell_conn_pattern RAIL707 -layers {M2} -rail_width {0.2 0.2}
set_pg_strategy S_RAIL707 -core -pattern {{name: RAIL707} {nets: {VDD VSS}}} -blockage $LowerBlockages
set_pg_strategy_via_rule V_RAIL707 -via_rule {
    {{{existing: strap} {layers: M3}} {strategies: S_RAIL707} {via_master: RAILV_1X1}}
    {{intersection: undefined} {via_master: NIL}}
}
compile_pg -strategies S_RAIL707 -via_rule V_RAIL707

# ---- 宏接入：M4 pin → M5 竖条 → M6 横条 ----
set_pg_via_master_rule MACROV_1X1 -via_array_dimension {1 1}
create_pg_macro_conn_pattern MACRO707_M5 -pin_conn_type long_pin -direction vertical \
    -layers M5 -pin_layers {M4} -width 0.28 -spacing interleaving -pitch 8 \
    -via_rule {{intersection: adjacent} {via_master: MACROV_1X1}}
set_pg_strategy S_MACRO707 -macros $Macros -pattern {{name: MACRO707_M5} {nets: {VDD VSS}}}
set_pg_strategy_via_rule V_MACRO707 -via_rule {
    {{{existing: strap} {layers: M6}} {strategies: S_MACRO707} {via_master: MACROV_1X1}}
    {{intersection: undefined} {via_master: NIL}}
}
compile_pg -strategies S_MACRO707 -via_rule V_MACRO707

save_block
save_lib
write_def pg_v6.def

redirect conn_v6.rpt {check_pg_connectivity -check_macro_pins all -check_std_cell_pins all}
check_pg_drc -output pg_drc_v6.txt
```

### 6.4 独立复查与定版决策（2026-11-11）

2026-11-11 用独立的 resume 流程对三个候选做了只读复查（每个候选都在新副本上重新执行 `check_pg_connectivity` 与 `check_pg_drc`），结果如下，**以本次复查为准**：

| 候选                 |  PG DRC | 浮空标准单元 VDD/VSS |          浮空 via VDD/VSS | 处理           |
| -------------------- | ------: | -------------------: | ------------------------: | -------------- |
| v6（原样，定版基线） | 200,206 |               0 / 63 |                     0 / 0 | **保留** |
| v6 + 补过孔          | 200,218 |               6 / 63 | 5,553 / 6,509（新增浮空） | 拒绝           |
| v7 + 补过孔          |   1,725 |    242,901 / 242,901 |                        — | 拒绝           |

三条判读：

- 三个候选的 `shorts` 均为 **0**，**短路清零这一结论不变**；
- v6 补过孔没有改善 DRC（200,206 → 200,218），反而**新引入 5,553 / 6,509 个浮空 via**，属负收益，拒绝；
- v7 系列 DRC 只有 1,725，但标准单元全浮空，供电连通失效，不可采用。

**数值差异说明**：构建会话内 `check_pg_drc -output` 的文本统计为 28,006（v6）/ 776（v7），独立复查为 200,206 / 1,725。差异原因尚未定论，目前有两个可疑点：

1. `-output` 的默认文件名是 `PG-errors_in_window.txt`，其语义可能只覆盖窗口/限量内的错误，不等价于完整错误集；
2. 构建会话内检查紧跟 `compile_pg`（编译期执行过 `Removing dangling/floating wire/vias after DRC check`），与保存后重新打开库再检查，几何状态可能不同。

**本报告中的相对结论（短路清零、宏全部连通、"层用错"是根因、v7 连通失效）不受影响**，受影响的只是 v6/v7 的绝对 DRC 计数。引用绝对数时以本次复查值（200,206 / 1,725）为准。

## 7. 遗留问题与 waiver

## 9. 方法论总结（可复用）

1. **工具 exit 0 ≠ 检查通过**：`compile_pg` 成功、`check_pg_drc` 退出码正常，都不能说明违规为 0，必须解析报告。
2. **先拿几何，再改参数**：本流程真正的转折点是 `check_pg_drc -output` 里的两条 bbox —— 一旦看到"0.28 竖条 × 1.33 水平条"，问题就从"神秘"变成"层用错了"。
3. **分段实验排除嫌疑**：只做 ring+mesh 就已经复现全部违规，直接排除 rails 和宏，省掉数轮无效改动。
4. **查库而不是猜**：标准单元 LEF 的 `PIN VDD/VSS` 层列表一行就确定了电源轨所在层，比反复试参数快得多。
5. **连通性与 DRC 要分开看**：v6/v7 是一对完美对照——同一套结构，一个连通但 DRC 高，一个 DRC 干净但连通失效；只看其中一个指标都会得出错误结论。
6. **`compile_pg` 会静默删除违规几何**：日志里的 `Removing dangling/floating wire/vias after DRC check` 必须关注，否则会把"被删掉的违规"误读成"修好了"。
7. **同一套检查要在"保存后重新打开"的副本上再跑一遍**：本报告 v6 的 DRC 在构建会话内统计为 28,006、独立复查为 200,206，正是因为统计口径/几何状态不同。凡是要写进报告的绝对数字，应以独立复查为准。
8. **"补孔"不是万能药**：v6 补过孔后 DRC 没降（200,206 → 200,218），却新增 5,553 / 6,509 个浮空 via。任何改动都要同时看 DRC 与连通性两个指标，只看一个必然误判。
