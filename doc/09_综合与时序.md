# 综合与时序估算

> 本文档在标准单元库到位前，用 **Artix-7 XC7A100T** 做资源与时序的**量级估算**。
> 库到位后把 `syn/run_synth.tcl` 的器件段替换为 `read_liberty` + `compile_ultra`
> 即可得到流片用的面积/功耗数据，文件列表与顶层名不变。

## 1. 怎么跑

```powershell
# 快速面积估算（只 synth，不布局布线，几分钟）
vivado -mode batch -source syn/run_synth_only.tcl

# 完整流程（synth + place + route，报告含真实 Fmax）
vivado -mode batch -source syn/run_synth.tcl
```

报告输出到 `syn/out/`：

| 文件 | 内容 |
|---|---|
| `utilization_synth.rpt` | LUT / FF / BRAM / DSP 用量 |
| `timing_synth.rpt` | 综合后时序估计 |
| `timing.rpt` / `timing_paths.rpt` | 布局布线后时序与关键路径 |
| `power.rpt` | 功耗估算 |
| `design_analysis.rpt` | 拥塞与逻辑层级 |
| `kwt_top_routed.dcp` | 可供后续检查的 checkpoint |

## 2. 约束

`syn/kwt_top.xdc`：

```tcl
create_clock -name clk -period 6.667 [get_ports clk]   # 150 MHz
```

`run_synth.tcl` 里额外加 0.6 ns 时钟不确定性（约 10 % 余量）和 2 ns 的
输入/输出延迟，模拟真实 SoC 边界。

## 3. 面积估算要点

按 150 MHz、W4A8 的架构，主要资源去向：

| 模块 | 主要资源 | 说明 |
|---|---|---|
| 4 × `kwt_dot64`（每个 GEMM engine 一套） | 256 个 8×4 乘法器 × 5 个 engine | DSP 或 LUT 实现，取决于工艺库 |
| `kwt_layernorm` | 4 路并行加法树 + 64 位乘法 | 64 位中间量占较多 FF |
| 操作数 buffer | ~40 KB SRAM | `act_buf` 12672 B、`wgt_buf` 8192 B、`score_buf` 19.8 KB、`p_buf` 9.8 KB |
| 参数 ROM（片外或片内） | 589824 nibble ≈ 295 KB | 若是片内需专用 SRAM 宏 |

> 面积能否压进 **2.25 mm²** 主要取决于：①乘法器用 DSP 还是标准单元；
> ②buffer 用 SRAM 宏还是寄存器堆；③参数 ROM 是否放在片外。
> 这三项都要等标准单元库与 SRAM 宏确认。

## 4. 实测结果

### 4.1 Artix-7 综合：RAM 无法映射到 BRAM

用 `synth_design -flatten_hierarchy none -directive runtimeoptimized` 跑 Artix-7，
综合在 RAM 映射阶段长时间无法收敛。日志（`syn/synth_run.log`）里共 **6 个 RAM 被
"dissolved into registers"**：

```
WARNING: [Synth 8-4767] Trying to implement RAM 'wgt_buf_reg' in registers.
Reason: 1. RAM has too many ports (16). Maximum supported = 16.
RAM "wgt_buf_reg" dissolved into registers
...
RAM "act_buf_reg" dissolved into registers
```

**原因**：`kwt_gemm_engine` 的 `act_buf`（最多 25344×8 bit）和 `wgt_buf`
（最多 16384×4 bit）在 GEMM 发射时需要 **64 路并行读**（`kwt_gemm4` 的 4 个
`kwt_dot64` × 64 通道），加上 1 路写，端口数远超 BRAM 能力，综合器只能退化成
触发器阵列。5 个 engine 实例叠加后规模爆炸，FPGA 综合不可行。

### 4.2 结论：必须用多端口 SRAM 宏

这不是 RTL 的功能问题（仿真全部 bit-exact），而是**存储实现**问题。到标准单元
库 + SRAM 宏到位后，需要做三件事之一：

| 方案 | 说明 | 代价 |
|---|---|---|
| **A. 多端口 SRAM 宏** | 定制 64 读 1 写的 SRAM（或 4 组 16 读 1 写 + 复制） | 面积换带宽，最直接 |
| **B. bank 化 + 时分复用** | 把 64 路并行读拆成 4 组 bank，每组 16 路，4 拍发完一个 64 点积 | 吞吐降 4×，周期从 9.85 ms 涨到约 39 ms |
| **C. 寄存器堆（小规模）** | `kwt_dot64` 的 64 个激活直接锁存进寄存器，weight 走 SRAM | 激活侧带宽天然满足，权重侧仍需多端口 |

推荐 **A**：`kwt_gemm4` 每个周期要吃 64 个激活 + 256 个权重 nibble，这是架构的
性能基础，降带宽等于放弃本轮所有优化成果。

### 4.3 其它综合警告（不影响功能）

```
WARNING: [Synth 8-7137] Register t_pipe_reg/g_pipe_reg/t_out_reg/g_out_reg
         has both Set and reset with same priority
```

`kwt_gemm_engine.v` 的发射计数器在复位和正常分支里都写 0，Vivado 提示可能造成
仿真/综合不匹配。实际 xsim 与参考模型逐位一致，判断为综合器对"异步复位 + 同步
清零"的保守提示，可忽略；若要彻底消除，把复位移到 `if (!rst_n)` 之外的
`else` 分支即可。

### 4.4 面积预估（定性）

在 SRAM 宏解决之前，无法给出可信的 mm² 数字。可以确定的量级：

- **存储**：`act_buf` 12672 B + `wgt_buf` 8192 B（× 5 engine，峰值）+ `score_buf`
  19800 B + `p_buf` 9804 B + 各层激活 ≈ **80–100 KB**，按 28 nm 6T SRAM
  (~0.15 µm²/bit) 约 **0.1–0.12 mm²**
- **计算**：5 套 `kwt_gemm4` × 256 个 8×4 乘法器 = 1280 个乘法器，是面积主要
  来源，按 28 nm 约 **0.6–0.9 mm²**
- **控制/其它**：约 **0.2 mm²**

合计落在 **0.9–1.2 mm²**，对 2.25 mm² 的预算有较大余量。等库到位后用
`run_synth.tcl` 拿准确值。
