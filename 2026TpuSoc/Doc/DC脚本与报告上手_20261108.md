# 从本项目学会独立出 DC 报告

日期：2026-11-08。对象：第一次接手综合与后端报告的队员。

目标是能自己找到输入、运行对应流程、读原生报告，并解释数字的范围和限制。下面对照本地脚本及已回传的服务器结果编写；没有在本机读取服务器 DDC 或重新运行服务器工具。

## 1. 先分清三件事

| 环节     | 本项目做什么                                                    | 工具                 | 当前实际状态                                                                      |
| -------- | --------------------------------------------------------------- | -------------------- | --------------------------------------------------------------------------------- |
| 逻辑综合 | 把 RTL 转成目标工艺的标准单元网表，接入 SRAM 宏，估算面积和时序 | DC / Design Compiler | 加速器和系统范围均已有映射网表及报告                                              |
| 形式等价 | 比较 RTL 与综合网表在所用建模、解释和设置下是否等价             | Formality / FM       | 加速器原生 match=1、verify=1；数组解释、宏边界和指导设置仍待审；不含 CPU/共享 TCM |
| 布局布线 | 在物理区域内放置宏和单元，构建时钟树、布线，再检查实际互连影响  | ICC2                 | 最新实测 v2 停在 LEF 双候选选择；v3 已准备，尚无服务器执行结果                    |

PR 是 place and route（布局布线），ICC2 是做这件事的工具。DC 里的单元已经选好了，但还没有完成真实物理摆放和连线。因此“DC 时序通过”和“布线后时序通过”是两个阶段的结论。

队友说“中端”，这次先把它落实为综合、约束和布局前报告。会读 DC 报告之后，再学 ICC2 各阶段报告。

## 3. 认识输入与输出

| 后缀                          | 在这里的含义                                                | 使用时要知道什么                                     |
| ----------------------------- | ----------------------------------------------------------- | ---------------------------------------------------- |
| `.sv` / `.v`              | RTL，或已经映射到标准单元的 Verilog 网表                    | 都可能叫 `.v`，要看内容、来源及是否实例化工艺单元  |
| `.db`                       | 综合/时序使用的二进制逻辑库，提供单元功能、时序、面积等信息 | 标准单元和两种 SRAM 都要有相应库；不是物理版图库     |
| `.sdc`                      | 时钟及输入输出等时序约束                                    | 是分析条件，决定 slack 的含义                        |
| `.ddc`                      | DC 设计检查点，包含设计及保存的约束等状态                   | 可重开检查点出报告，不必每次从 RTL 综合              |
| `.rpt`                      | 工具生成的文本报告                                          | 要看顶层、单位、分析条件和具体路径                   |
| `.saif`                     | 仿真得到的开关活动统计                                      | 关联任务和仿真窗口；要核对名称映射、默认活动和未知态 |
| `.svf`                      | 综合过程产生、供 Formality 使用的指导信息                   | 不是时序约束，也不是仿真波形                         |
| `.lef` / `.tf` / `.ndm` | 物理几何、工艺技术或 ICC2 库资料                            | 用于物理实现，不能仅凭文件存在认定与网表兼容         |

一个 DC 结果至少要同时说清：**设计版本、顶层/范围、库与工艺角、约束、工具阶段、原始报告路径**。

## 4. 用实际代码读懂系统综合

先理解以下主干，再回看 `System.tcl` 的检查逻辑。以下摘录用于阅读，不能作为独立脚本直接运行。

```tcl
set target_library [list $::env(TPU_STDCELL_DB)]
set link_library [concat [list *] $target_library \
    [list $::env(TPU_SRAM_DB) $::env(TPU_SYSTEM_DB)]]
source [file join [file dirname $Out] Sources.tcl]
analyze -format sverilog -define {SYNTHESIS FPGA FPGA_SOURCE} -library WORK $Sources
elaborate e203_cpu_top -library WORK
current_design e203_cpu_top
link
create_clock -name CoreClock -period 6.666667 [get_ports clk]
compile_ultra -no_autoungroup -no_boundary_optimization
write -hierarchy -format ddc -output candidate.ddc
report_area -hierarchy > area.rpt
report_timing -delay_type max -max_paths 20 -significant_digits 6 > setup.rpt
```

| 命令/变量          | 在本项目里的作用                                                    |
| ------------------ | ------------------------------------------------------------------- |
| `target_library` | 指定逻辑综合可映射到的标准单元库                                    |
| `link_library`   | 帮助解析已有标准单元、SRAM 等引用；`*` 表示也查内存中已读入的设计 |
| `source`         | 执行另一个 Tcl 文件；这里装入源码清单，不是启动仿真                 |
| `analyze`        | 按指定语言及宏定义分析源码                                          |
| `elaborate`      | 按顶层和参数展开设计层级                                            |
| `current_design` | 选择后续命令操作的设计                                              |
| `link`           | 解析模块与库单元引用；引用缺失要处理，不能继续抄结果                |
| `create_clock`   | 告诉工具时钟端口和周期；不会生成实际时钟树                          |
| `compile_ultra`  | 优化逻辑并映射到目标工艺单元                                        |
| `write`          | 保存设计检查点或网表                                                |
| `report_*`       | 查询并输出当前设计的报告                                            |

Tcl 最少语法：`set A 1` 是赋值，`$A` 是取值，`[...]` 是先执行内部命令并使用结果，`{...}` 通常用于原样分组。这里的 `>` 由 DC 命令将报告写入文件。服务器 bash 和 DC 的 Tcl 提示符不能混用。

实际 `System.tcl` 比摘录多了重要步骤：

1. 从 `Sources.tcl` 读 CPU/互连及已经冻结的加速器网表；并不是这一步把整个加速器 RTL 再综合一次。
2. 要求私有 SRAM 56 个、共享 SRAM 64 个，并保护宏与冻结加速器。
3. 综合后先保存 `baseline.*`；若发现 hold 负裕量，尝试仅针对 hold 的增量综合，再保存 `candidate.*`。
4. 检查冻结加速器叶单元名称和引用未改变，重新核对 SRAM 数量，输出面积、时序、约束及设计检查。

因此交接时要写清是 `baseline` 还是 `candidate`。保存过网表不代表后面的检查已全部通过，脚本结束码和原生日志也要看。

源码中的 `FPGA` / `FPGA_SOURCE` 是当前系统平台采用的宏定义名字；本轮实际映射目标由 SMIC RVT 库和 SRAM 绑定决定。不要单凭宏名判断它是一次 FPGA 综合，也不要未理解条件编译就删掉宏。

## 5. 约束就是“我们按什么条件检查”

当前两个综合范围的预算相同，时钟输入名不同：加速器是 `nice_clk`，系统是 `clk`。

| 项目                 |     代码中的值 | 含义                                          |
| -------------------- | -------------: | --------------------------------------------- |
| 时钟周期             |    6.666667 ns | 约 150 MHz 的目标周期                         |
| setup uncertainty    |       0.200 ns | setup 分析预留的时钟不确定性预算              |
| hold uncertainty     |       0.100 ns | hold 分析预留的时钟不确定性预算               |
| clock transition     |          0.100 | 时钟边沿转换时间；以工具时间单位为准          |
| input delay max/min  |  1.000 / 0.100 | 外部输入相对时钟的最晚/最早到达预算           |
| output delay max/min | 1.000 / -0.100 | 接收端对输出的 setup/hold 预算                |
| input transition     |          0.100 | 输入信号转换时间假设                          |
| output load          |          0.035 | 输出负载假设；先读 `units.rpt` 确认电容单位 |

这些是工程预算，不是测出来的板级时序。负的 output min delay 是时序接口预算的表达方式，不能看到负号就认定是错误或负 slack。

原系统脚本把所有输出统一当成数据输出。后续复核确认 `inspect_core_clk`、`core_csr_clk` 是 `clk` 的直接转发，因此撤掉它们的数据 output delay，建立两个同源、除 1 的 generated clock，保留原输出负载。其他数据预算及网表保持不变，配套程序检查 SDC 差异。

复核后工具会看到 1 个根时钟和 2 个转发时钟对象，不能写成“三个独立时钟域”。应使用复核后的时序报告，不能将原系统 `mapped/hold.rpt` 与复核后的正裕量混作同一份结果。

## 6. 报告应该按什么顺序看

| 文件                                 | 先回答的问题                                     |
| ------------------------------------ | ------------------------------------------------ |
| `dc.log`、运行摘要                 | 读的哪个设计？是否出现 Error？最后到达哪个阶段？ |
| `units.rpt`                        | 时间、电容等采用什么单位？                       |
| `check_design.rpt`                 | 设计结构/连接检查发现了什么问题？                |
| `check_timing.rpt`                 | 有没有缺时钟、缺约束等需要解释的问题？           |
| `clocks.rpt`、SDC                  | 分析的是哪些时钟，周期和预算是什么？             |
| `setup.rpt`                        | 最晚到达路径是否满足 setup？                     |
| `hold.rpt`                         | 最早到达路径是否满足 hold？                      |
| `constraint_violations.rpt`        | 还有哪些约束违例，例如转换时间、负载等？         |
| `qor.rpt`                          | 综合质量概览，具体栏目按原生报告读取             |
| `area.rpt`、`area_breakdown.tsv` | 总量和不同边界的面积分别是多少？                 |

不是每个目录都有全部文件：系统原综合的 `units.rpt` 在原 `mapped` 目录，时钟端口复核目录有新时序及互斥面积分项。

一条时序路径至少读六项：

1. `Startpoint`：从哪里出发，例如寄存器或输入端口。
2. `Endpoint`：到哪里接收，例如寄存器或输出端口。
3. `Path Group`、`Path Type`：属于哪个组，分析 max 还是 min。
4. 中间单元/网络：延迟花在哪里。
5. `data arrival time`、`data required time`：实际计算的到达时间和要求时间。
6. `slack`：裕量及 `MET` / `VIOLATED`。

setup 可以先理解为“数据不能太晚到”，通常 slack = required − arrival；hold 是“数据不能太早变”，通常 slack = arrival − required。实际还包含时钟路径和库时序要求，应从报告读完整算式，不要只用周期减组合逻辑延迟。

WNS 是最差时序裕量指标；正数说明所报告分析条件下该检查有余量。`-max_paths 20` 只是限制输出路径数，不能据此声称全设计只有 20 条路径或只有 20 个违例。检查完整性和其他违例还要看对应报告。

## 8. 第二课：从已有 DDC 重新生成报告

先读懂第一课，再运行这一步。沿用已经实际验证的 `ClockPortReview` 流程，不急着从 RTL 重跑综合。

顺序是：核验原输入 → 创建新结果目录 → 配置三个逻辑库 → `read_ddc` → `current_design` / `link` → 核对宏与时钟 → 复核两个时钟输出角色 → `report_*` → 检查网表与其他数据预算未变 → 保存报告。

`read_ddc` 返回设计列表，不应当作布尔成功码直接判断；我们用设计对象是否存在及 `link` 等结果核对。已有 DDC 保存了约束，不能盲目再 `source` 一遍任意 SDC，否则可能产生重复或冲突。

实际源码 `ClockPortReview.tcl` 没有 `analyze`、`elaborate`、`compile`；它是“从检查点重新分析出报告”。配套 `ClockPortReview.py` 还做输入 SHA、SDC 差异、面积分项与汇总核验。正式复现应保留这些检查，不能为了脚本短删掉。

第二课验收：能自己指出每个输入从哪里来，运行后定位新目录，找到原生报告，解释与上一份是否一致。若失败，先区分输入校验、读库/链接、时序分析还是汇总归档阶段，再决定是否重跑。

## 9. 当前结果，用来检查是否读对版本

以下来自已回传并登记的服务器结果，第一课仍需对照原始文件核对。

| 指标                          |            当前结果 | 范围和条件                                                     |
| ----------------------------- | ------------------: | -------------------------------------------------------------- |
| 加速器计分面积                | 0.703272383184 mm² | 新增加速器逻辑/接口及 56 个私有 SRAM 宏                        |
| 其中私有 SRAM                 | 0.512317367184 mm² | 112 KiB；已包含在上一行                                        |
| 系统映射总面积                | 2.495814810768 mm² | E203/内部 ICB、加速器、私有及共享 SRAM 等；外部固定外设未纳入  |
| 系统 setup WNS                |      +0.00191832 ns | 时钟端口复核后，TT、布局前、理想时钟                           |
| 系统 hold WNS                 |    +0.0000830591 ns | 同上                                                           |
| FF1 系统平均功耗估算          |       34.2612452 mW | 对应任务 SAIF，CPU/加速器/120 个 SRAM 宏；仍有默认/X活动审查项 |
| 单层 encoder 系统平均功耗估算 |       32.7035243 mW | 同上，使用该任务自己的 SAIF                                    |

setup 余量约 1.918 ps，hold 余量约 0.083 ps，非常小。不能仅凭这两个正数承诺布线后仍通过。

面积单位换算：1 mm² = 1,000,000 µm²。层级面积父项可能已包含子项，不要把父项和子项全部加一次。互斥分项由 `AreaBreakdown.tcl` 逐叶归类，同一个叶单元只计一次。

2.25 mm² 预算比较的是加速器逻辑/新增接口/私有 SRAM 小计，不能直接拿系统 2.4958 mm² 判断超预算。映射单元面积也不能叫做 die/core 面积；后者还受留白、宏布局、供电和布线要求影响。

## 10. 后续两课与报告写法

第三课读功耗：讲清动态/泄漏、SAIF 任务窗口、名称映射、用户/传播/默认活动、未知态。先确认活动质量，再读 `report_power`；对象覆盖比例不是功耗误差上限。当前功耗源目录是 `~/soc/tpusoc_system_power_auto_active_20261107_EQ6eDI`。

第四课接 ICC2：从实际成功的建库/链接、初始 floorplan 开始，逐阶段区分宏放置、标准单元 placement、CTS、route。先取得每一阶段的真实检查点，再把布局图、拥塞、时序和检查报告写入技术报告。

报告中的每个结论采用“对象 + 条件 + 数字 + 原始来源 + 限制”的句式，例如：

> 对 e203_cpu_top 的冻结候选，在 SMIC 40 nm RVT、TT 1.1 V/25℃、目标约 150 MHz 的布局前理想时钟分析中，时钟端口复核后的 setup/hold WNS 分别为 +0.00191832 ns / +0.0000830591 ns。来源为 TiLrj3 目录的 setup.rpt、hold.rpt 及配套约束；尚不代表 CTS/布线后签核。

能独立回答以下问题，就能与队友进行有效核对：综合哪个顶层？用了什么库？报告分析条件是什么？这个面积包括谁？最差路径从哪里到哪里？结果属于哪个阶段？有没有尚未解释的错误或限制？
